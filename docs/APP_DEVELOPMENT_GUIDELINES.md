# 集卡 App 开发决策与规范

> 文档状态：已确认，作为 App 开发的基础约束  
> 首次制定：2026-07-17  
> 适用范围：iOS、Android Flutter App 及其服务端接口  
> 当前目标：先完成底部导航栏与首页原型，用真机效果验证 Flutter 路线是否可行

> 阶段更新（2026-07-17）：项目所有者已确认进入正式公开数据接口接入阶段；第 7 节保留为第一版原型的历史范围，不再代表当前开发范围。

## 1. 项目定位

集卡 App 是现有 `card.lengziyu.cn` Web 项目的移动端客户端，核心价值是帮助用户浏览、整理和比较卡片信息。

App 必须始终定位为：

- 卡片信息展示与整理工具；
- 基于公开资料的卡片比较工具；
- 用户自主管理个人卡片收藏的工具；
- 不经手资金、不提供金融服务的信息型产品。

现有 Vue Web 站点和管理后台继续独立维护。Flutter App 是新的客户端实现，不替换现有网站，也不把管理后台迁入 App。

## 2. 已确认且不可擅自变更的决定

### 2.1 开发者与运营主体

- iOS 和 Android 始终使用个人开发者账号发布；
- 不计划成立公司或改为组织账号运营；
- App Store 上显示个人开发者法定姓名是可接受结果；
- 不以融资、规模化商业运营或金融业务为目标；
- 后续开发不得以“未来成立公司”为前提引入超出个人开发者边界的功能。

### 2.2 商业化与独立性原则

> 阶段更新（2026-07-20）：项目所有者已确认启动最小 Pro 会员版本。Pro 仅销售持续的软件工具与云服务权益，不改变本 App 的独立信息工具定位。

当前允许通过 App Store 与 Google Play 的应用内购买提供 Pro 会员，但必须满足：

- 免费版继续完整提供公开卡片资料、来源、更新时间、风险提示与基础浏览；
- Pro 权益优先用于高级展示模式、同步、提醒、深度对比、历史数据、离线与导出；
- Pro 可以提供用户主动上传的消费账单截图结构化分析，但必须遵守第 5 节的数据最小化规则，AI 只做字段提取，金额与费率由可复现公式计算；
- 正式支付接入前只允许展示明确标记的内测预览，不得伪造购买成功或会员状态；
- 数字权益必须使用目标商店允许的支付系统，并提供恢复购买、订阅管理和取消入口；
- 价格、周期、自动续费规则和试用结束后的扣费必须清晰展示；
- 会员状态必须以商店交易和服务端权益校验为准，不能仅依赖本地布尔值；
- 不提供付费下载；
- 不接入广告；
- 不接受品牌赞助排名；
- 不使用 Affiliate、CPA、返佣或收入分成链接；
- 不出售用户数据；
- 不因为商业合作改变卡片排行、推荐或评价；
- 不在 App 内引导用户绕过应用商店购买数字内容。

邀请码与邀请链接属于高风险展示字段：可在后台保存以便人工核验，但必须默认不公开。只有经运营逐项确认其不含返佣、Affiliate、CPA、推广追踪或隐藏跳转时，才可通过后台的卡片/文章独立开关显示；Flutter 与公开 API 必须以服务端开关为准，不能自行缓存或绕过该隐藏状态。

App 可以提供卡片官方页面或官方申请页面的普通外链，但必须满足：

- 链接直接指向可验证的官方来源；
- 不包含个人邀请码、返佣参数或隐藏跳转；
- 不宣称与发卡方存在官方合作；
- 不保证用户能够申请成功；
- 跳转前后不得收集用户在第三方网站提交的资料。

扩大 Pro 范围或正式开放购买前，必须单独进行商店政策、隐私、税务和法律风险评估，不能在普通功能开发中顺带加入新的收费模式。

### 2.3 技术路线

- 移动端统一使用 **Flutter** 开发；
- 使用 Dart，不使用 Vue WebView 套壳作为 App 主体；
- iOS 与 Android 共用一套 Flutter 业务代码和设计系统；
- 用户体验和 UI 质量优先于开发速度与代码复用率；
- 现有 Vue 页面只作为内容、视觉和交互参考，不直接复制 DOM、CSS 或浏览器手势实现；
- 核心页面必须使用 Flutter 原生组件、绘制和手势系统重新实现；
- App 代码位于独立 `card-app` 仓库根目录；不得修改或破坏现有 Vue Web 项目的构建与部署。

“体验优先”意味着：如果代码复用与滚动、动画、手势、无障碍或平台习惯冲突，应优先保证最终体验。

## 3. 产品与合规边界

为了保持个人开发者和信息工具定位，以下边界属于硬限制。

### 3.1 允许实现

- 浏览卡片目录；
- 搜索、筛选和排序；
- 展示费用、返现、地区、KYC、支付渠道等公开资料；
- 基于明确规则进行卡片对比和费用计算；
- 收藏、浏览历史和手动维护“我的卡片”；
- 展示资料来源、最后核验时间和变更记录；
- 提醒用户查看官方最新规则；
- 提供用户纠错和反馈入口；
- 提供非商业、非保证性质的信息匹配结果。

### 3.2 禁止实现

- 不发行银行卡、虚拟卡或支付账户；
- 不代办开卡，不替用户提交申请；
- 不采集或保存身份证、护照、人脸、地址证明等 KYC 材料；
- 不保存完整银行卡号、有效期、CVV、PIN；
- 不索取网银、钱包、交易所密码或助记词；
- 不提供充值、转账、换汇、交易、提现、托管或清算；
- 不连接用户银行或交易所账户自动拉取资产及交易；
- 不参与贷款导流、授信、信用评估或开卡审批；
- 不提供投资建议、收益承诺或“保证下卡”结论；
- 不把推荐结果描述为受监管的金融建议。

所有卡片详情应保留类似以下提示：

> 本 App 仅整理公开信息，不提供金融服务。卡片费用、地区限制、KYC 和申请结果均以发卡方最新官方规则为准。

卡片名称、图片、标识、费用与权益等内容整理自官方网站及其他公开信息，仅用于信息展示与比较；相关商标、图片和名称归其权利人所有。如展示存在错误、侵权或造成冒犯，应提供清晰的反馈与纠错入口，核实后及时更正或下架。

## 4. 账号与登录规范

### 4.1 现有 Web 认证服务审计结论（2026-07-17）

> 阶段更新（2026-07-23）：项目所有者决定改用 Supabase Auth。第一阶段使用官方托管项目，Flutter 与服务端采用 Supabase access token，Firebase 仅保留迁移兼容；认证基础设施和真机回归现在开始准备，旧用户迁移与关闭 Firebase/旧密码认证安排在正式上线前 1–2 天。启用与迁移必须遵循 [`SUPABASE_AUTH.md`](SUPABASE_AUTH.md)。

当前 `card.lengziyu.cn` 用户名/邮箱认证服务不批准接入 Flutter App。已确认的主要阻断项包括：

- 密码使用快速 SHA-256 摘要，缺少适用于密码的慢哈希与独立盐值；
- 会话令牌随机强度不足，且令牌以原值保存；
- 旧 Web 认证缺少邮箱所有权验证、密码重置、App 内账号删除和全会话撤销闭环；Supabase 路径正在补齐这些能力，但自托管生产部署和真机审计尚未完成；
- Web 客户端把 Bearer Token 放入普通 Local Storage，不能沿用到移动端；
- 现有测试只覆盖基础注册、登录和会话隔离，未覆盖上述安全与账号生命周期要求。

服务端已有 HTTPS 部署配置、基础安全响应头和按 IP 的认证限流，但不足以抵消以上风险。在阻断项完成整改、安全测试和迁移方案评审前：

- Flutter 只实现登录/注册 UI 与本地表单校验；
- 表单不得调用现有认证 API，不得创建虚假登录态；
- 输入的账号和密码不得写入文件、偏好设置、日志或分析事件；
- 用户提交预览表单后必须清空密码并明确说明未发送、未保存；
- 未登录状态仅展示只读演示卡片，不显示“已加入我的卡片”等个人归属状态；新增、收藏等个人操作必须先登录并完成邮箱验证。
- 阶段更新（2026-07-23）：已验证 Supabase 账号的卡片、收藏、浏览历史、纠错、推荐与留言通过对应 HTTPS 接口同步；移动端仅使用 Keychain/Keystore 中的短期 access token。未登录、未验证、离线或服务不可用时不得上传，且不得将本机缓存表述为云端同步成功。

正式接入前至少需要采用 Argon2id、scrypt 或经评审的同级密码哈希方案，使用高熵不可预测会话令牌并安全保存，补齐邮箱验证、密码重置、账号删除、会话撤销和审计测试；移动端 Token 必须进入 Keychain/Keystore。

规划支持以下登录方式：

1. Google 账号登录（Google Sign-In，不表述为“Gmail 密码登录”）；
2. Apple 账号登录（Sign in with Apple）；
3. 用户名 + 密码登录；
4. 邮箱 + 密码注册和登录；
5. 邮箱验证与密码重置。

账号系统必须满足：

- Apple 登录与 Google 登录具有等价入口和基本能力；
- 一个用户账号可以绑定多个登录方式，避免产生多个孤立账号；
- 第三方账号以服务商返回的稳定用户 ID 为准，不能只用邮箱判断身份；
- 用户名大小写不敏感且全局唯一；
- 邮箱保存前进行规范化，并完成所有权验证；
- 密码只在服务端保存安全哈希，不得明文保存或记录；
- 登录 Token 在移动端使用 iOS Keychain / Android Keystore 对应的安全存储，不使用普通本地配置文件；
- 卡片、收藏、历史和投稿等本地缓存必须按认证服务返回的稳定用户 ID 隔离；退出或切换账号时立即清空内存中的上一账号状态，异步响应和排队写入必须再次核对发起时的用户 ID；
- 旧账号数据不得仅凭相同邮箱自动合并到 Supabase、Google、Apple 或其他新身份；迁移必须经过单独确认并验证旧、新身份归属；
- 不在日志、崩溃报告或分析事件中记录密码、Token 和完整邮箱；
- 支持退出登录、撤销第三方绑定和 App 内删除账号；
- 删除账号时同步删除或匿名化该用户的收藏、历史及其他个人数据；
- 第一版首页原型不要求实现登录，但后续架构不得阻碍以上能力。

## 5. 隐私与数据最小化

- 只收集账号、同步和用户主动提交功能所必需的数据；
- 不申请通讯录、相册、定位、麦克风、相机等与核心功能无关的权限；
- 消费账单分析只允许通过系统照片选择器处理用户主动选择的单张图片，不后台扫描相册，不保存原图；上传前必须提示用户移除姓名、完整卡号、订单号、地址和二维码等不必要信息；
- 卡友技巧投稿使用“必填标题 + 关联卡片 + 最多 2000 字自由经验描述”的简化表单，标题最多 80 字，不强制拆分步骤、适用条件或注意事项；允许通过系统照片选择器主动选择最多三张辅助说明图片，不后台扫描相册；客户端必须限制格式与大小，上传前提示遮挡姓名、完整卡号、订单号、地址、二维码和联系方式，文字与图片随投稿进入审核且不得在审核通过前公开；
- 图片发送到第三方 AI 前必须取得用户明确确认，并在隐私政策中披露处理目的、数据类型、第三方处理方和保留策略；AI API 密钥只能保存在服务端；
- 账单结构化结果最多保留卡号末四位，禁止提取或保存完整卡号、CVV、有效期、PIN、账号凭据或身份材料；
- 第一版不接入广告 SDK、用户画像 SDK或跨 App 追踪；
- 第一版不接入非必要的第三方行为分析 SDK；
- 崩溃监控如后续接入，必须过滤账号、Token、邮箱和用户输入；
- 收藏、浏览历史默认属于用户个人数据，不用于出售、广告定向或商业推荐；
- 上架前必须准备可公开访问的隐私政策、用户协议和账号删除说明；
- API 全程使用 HTTPS，生产环境不得使用测试证书或关闭证书校验。

## 6. UI 与用户体验规范

### 6.1 设计原则

- 以现有移动端 Web 视觉为第一版参考，保持品牌、色彩、卡面和整体氛围；
- 复刻的是视觉意图和信息层级，不是机械复制 CSS 像素；
- iOS 和 Android 可以在返回手势、触觉反馈、系统弹窗等方面遵循各自平台习惯；
- 页面必须适配刘海、Dynamic Island、圆角屏、底部手势区和 Android 系统栏；
- 所有主要点击区域不小于 44×44 逻辑像素；
- 页面必须支持系统字体缩放，关键内容不得因大字体被截断；
- 颜色和文字对比度应满足基本无障碍要求；
- 图标按钮必须提供语义标签；
- 支持系统“减少动态效果”设置，为复杂动画提供降级模式；
- 加载、空状态、失败、离线和重试状态必须作为正式 UI 设计，而不是临时提示；
- 动画用于表达层级与状态变化，不为了展示技术而阻碍操作。
- 首页“堆叠”和“聚焦”模式不得增加模式名称、卡片名称、页码或总数、上一张或下一张按钮、滑动提示及其他说明文字；卡片切换只通过卡面直接手势、位移和层级反馈及触觉反馈表达。除非项目所有者明确修改本条，后续不得以增强可发现性或优化交互为由增加上述 UI。

### 6.2 性能目标

- 常规滚动和页面切换以稳定 60 FPS 为最低目标；
- 支持高刷新率设备时，应争取 90/120 FPS；
- 首屏不得等待全部卡片图片下载完成后才显示；
- 图片按显示尺寸解码并使用缓存，避免加载原始超大图；
- 重绘范围应受控，避免整个页面因单个动画持续重绘；
- 动画和手势必须在至少一台真实 iPhone 与一台中低端 Android 真机验证；
- 不能只以模拟器流畅作为验收依据；
- 性能不达标时优先降低非必要粒子数量、模糊半径或背景复杂度，不牺牲触控响应。

## 7. 第一版 Flutter 原型范围

第一版不是完整 App，也不是上架版本。它的唯一目标是验证 Flutter 能否高质量复刻当前首页体验。

### 7.1 必须完成

- 建立可分别运行于 iOS 和 Android 的 Flutter 工程；
- 建立基础主题、颜色、字体、间距和图标规范；
- 复刻全屏背景、氛围光效和安全区处理；
- 复刻首页顶部区域：
  - “我的卡片”标题；
  - 当前用户/演示状态说明；
  - 右上角添加按钮；
- 复刻首页主体：
  - 卡片堆叠展示或空状态；
  - 基本进入动画；
  - 点击、按压反馈；
- 复刻底部导航栏：
  - 我的卡片；
  - 市场；
  - 排行榜；
  - 我的；
  - 独立的添加按钮；
- 首页导航项需要有选中状态、按压反馈和正确的安全区间距；
- 非首页导航项第一版可以进入统一占位页，但不能出现无响应点击；
- 使用本地 Mock 数据，不依赖生产 API；
- 同时提供“有卡片”和“无卡片”两种可验证状态；
- 在至少一台 iPhone 和一台 Android 真机上录制或截图对比现有 Web 版本。

### 7.2 第一版明确不做

- 不实现注册和登录；
- 不接入 Google Sign-In 或 Sign in with Apple；
- 不接入正式 API 和账号同步；
- 不迁移市场、排行、详情、文章和个人中心业务；
- 不实现管理后台；
- 不实现推送、深链、订阅、支付或广告；
- 不追求一次性迁移 Three.js 粒子卡片效果；
- 不为了赶进度使用整页 WebView。

## 8. 当前公开接口接入阶段（2026-07-17）

项目所有者已授权 Flutter App 接入 `card.lengziyu.cn` 的生产公开数据接口。当前允许接入：

- 卡片目录、筛选、排序和卡片详情；
- 首页默认卡片与列表顺序配置；
- 热门排行、稳定币总览与单项趋势、卡片数据榜；
- 公开文章列表、详情、浏览次数与点赞；
- 健康检查等不涉及用户身份和管理权限的只读接口。

接口基地址默认使用 `https://card.lengziyu.cn`，并允许通过构建参数切换测试环境。生产环境必须继续使用 HTTPS，不得绕过证书校验。

第 4.1 节旧认证审计结论仍然有效，旧密码会话不得接入 Flutter。阶段更新（2026-07-23）：经 Supabase access token 校验的用户卡片状态、文章收藏、纠错、推荐和留言接口可以接入；管理端接口不得进入 Flutter App。未登录用户只可浏览演示内容，个人写操作必须进入登录与邮箱验证流程。

## 8. 第一版验收标准

满足以下条件后，才能判断 Flutter 方案可行并进入下一阶段：

- iOS 和 Android 均能独立构建、安装和启动；
- 首页布局与现有 Web 版在信息层级、品牌氛围和主要尺寸关系上基本一致；
- 底部导航不会被系统手势区遮挡；
- 列表滚动、页面切换、卡片按压没有明显掉帧或延迟；
- 无卡片状态和有卡片状态都完整可用；
- 深色背景、渐变、玻璃效果在两端无明显色差或渲染异常；
- 开启大字体和减少动态效果后仍能完成基本操作；
- 首页没有 WebView、DOM 或远程网页依赖；
- Flutter 原型不会修改或破坏现有 Vue Web 项目。

如果第一版未达到体验要求，应先定位是实现问题、资源问题还是 Flutter 渲染限制，再决定是否继续；不得因为已经投入开发而默认进入全量迁移。

### 10.1 AI 选卡匹配（2026-07-22 已确认）

- 已登录、完成邮箱验证且具有有效 Pro 权益的用户，可以主动填写所在地、可用证件、用途和 KYC 偏好，请求 AI 从集卡公开卡片目录中筛选最多三张“值得进一步了解”的卡片；
- 此功能不是申请代理、审批、授信或投资建议，不保证可申请、可获批或任何费用、额度、收益结果；
- 请求只包含用户主动选择的条件和最多 500 字的补充说明；禁止填写、上传或在服务端持久化身份证件号码、完整卡号、密码、助记词或其他凭据；
- 服务端只向 AI 提供已公开的卡片摘要，使用严格 JSON 输出并二次过滤，仅允许返回当前目录中真实存在的卡片 ID；
- API 密钥只保存在服务端环境变量中；选卡请求不得写入用户档案、日志或分析系统，响应设置为不缓存；
- 每次结果必须显示“以发行方官方页面为准”的提示，并为用户提供打开卡片资料的入口。

### 10.2 AI 开卡准备（2026-07-23 已确认）

- 该功能只面向已登录、完成邮箱验证且具有有效 Pro 权益的用户；Flutter 入口与服务端 API 必须同时校验，不得仅依赖本地布尔值；
- 用户主动选择目标卡片、居住地、申请主体、可用材料类型和当前阶段，第一版只提供引导式问答与一次性准备清单，不提供无限对话；
- 服务端必须优先检索已发布的项目文章：先匹配 `relatedCardIds`，再按 `open-card` 分类、标签、标题和正文相关性排序；
- 只有当项目文章缺失、过期、相互冲突或无法覆盖用户问题时，才可联网补充；联网来源只允许目标卡片发行方官网、官方帮助中心或官方申请说明；
- 结果必须分别标明“项目文章”与“官方网页”来源，并返回步骤、风险、无法确认项和下一步，不得把不同来源混合成无法追溯的结论；
- 该功能仅提供公开资料整理和申请准备提醒，不代办、不自动填写或提交申请，不提供通过率、额度或审批结果预测，不保证开卡成功；
- 禁止上传证件、人脸或地址证明图片；自由文本最多 500 字，必须在发送前阻断证件号、完整卡号、密码、验证码、私钥和助记词等敏感内容；
- 用户输入和 AI 结果不得写入用户档案、分析系统或正文日志，响应必须使用 `Cache-Control: no-store`。
