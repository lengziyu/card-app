# 集卡 App 开发决策与规范

> 文档状态：已确认，作为 App 开发的基础约束  
> 首次制定：2026-07-17  
> 适用范围：iOS、Android Flutter App 及其服务端接口  
> 当前目标：先完成底部导航栏与首页原型，用真机效果验证 Flutter 路线是否可行

## 1. 项目定位

集卡 App 是现有 `card.lengziyu.cn` Web 项目的移动端客户端，核心价值是帮助用户浏览、整理和比较卡片信息。

App 必须始终定位为：

- 卡片信息展示与整理工具；
- 基于公开资料的卡片比较工具；
- 用户自主管理个人卡片收藏的工具；
- 不经手资金、不提供金融服务的信息型产品。

现有 Vue Web 站点和管理后台继续独立维护。Flutter App 是新的客户端实现，不替换现有网站，也不把管理后台迁入 App。

## 2. 已确认且不可擅自变更的决定

### 2.1 开发者与运营主体

- iOS 和 Android 始终使用个人开发者账号发布；
- 不计划成立公司或改为组织账号运营；
- App Store 上显示个人开发者法定姓名是可接受结果；
- 不以融资、规模化商业运营或金融业务为目标；
- 后续开发不得以“未来成立公司”为前提引入超出个人开发者边界的功能。

### 2.2 非商业化原则

当前项目不开展商业化行为，包括但不限于：

- 不提供付费下载；
- 不提供 App 内购买或自动续费订阅；
- 不接入广告；
- 不设置付费会员或付费功能墙；
- 不接受品牌赞助排名；
- 不使用 Affiliate、CPA、返佣或收入分成链接；
- 不出售用户数据；
- 不因为商业合作改变卡片排行、推荐或评价；
- 不在 App 内引导用户绕过应用商店购买数字内容。

App 可以提供卡片官方页面或官方申请页面的普通外链，但必须满足：

- 链接直接指向可验证的官方来源；
- 不包含个人邀请码、返佣参数或隐藏跳转；
- 不宣称与发卡方存在官方合作；
- 不保证用户能够申请成功；
- 跳转前后不得收集用户在第三方网站提交的资料。

如未来希望改变非商业化原则，必须先修改本文件并单独进行商店政策、隐私和法律风险评估，不能在普通功能开发中顺带加入。

### 2.3 技术路线

- 移动端统一使用 **Flutter** 开发；
- 使用 Dart，不使用 Vue WebView 套壳作为 App 主体；
- iOS 与 Android 共用一套 Flutter 业务代码和设计系统；
- 用户体验和 UI 质量优先于开发速度与代码复用率；
- 现有 Vue 页面只作为内容、视觉和交互参考，不直接复制 DOM、CSS 或浏览器手势实现；
- 核心页面必须使用 Flutter 原生组件、绘制和手势系统重新实现；
- App 代码位于独立 `card-app` 仓库根目录；不得修改或破坏现有 Vue Web 项目的构建与部署。

“体验优先”意味着：如果代码复用与滚动、动画、手势、无障碍或平台习惯冲突，应优先保证最终体验。

## 3. 产品与合规边界

为了保持个人开发者和信息工具定位，以下边界属于硬限制。

### 3.1 允许实现

- 浏览卡片目录；
- 搜索、筛选和排序；
- 展示费用、返现、地区、KYC、支付渠道等公开资料；
- 基于明确规则进行卡片对比和费用计算；
- 收藏、浏览历史和手动维护“我的卡片”；
- 展示资料来源、最后核验时间和变更记录；
- 提醒用户查看官方最新规则；
- 提供用户纠错和反馈入口；
- 提供非商业、非保证性质的信息匹配结果。

### 3.2 禁止实现

- 不发行银行卡、虚拟卡或支付账户；
- 不代办开卡，不替用户提交申请；
- 不采集或保存身份证、护照、人脸、地址证明等 KYC 材料；
- 不保存完整银行卡号、有效期、CVV、PIN；
- 不索取网银、钱包、交易所密码或助记词；
- 不提供充值、转账、换汇、交易、提现、托管或清算；
- 不连接用户银行或交易所账户自动拉取资产及交易；
- 不参与贷款导流、授信、信用评估或开卡审批；
- 不提供投资建议、收益承诺或“保证下卡”结论；
- 不把推荐结果描述为受监管的金融建议。

所有卡片详情应保留类似以下提示：

> 本 App 仅整理公开信息，不提供金融服务。卡片费用、地区限制、KYC 和申请结果均以发卡方最新官方规则为准。

## 4. 账号与登录规范

规划支持以下登录方式：

1. Google 账号登录（Google Sign-In，不表述为“Gmail 密码登录”）；
2. Apple 账号登录（Sign in with Apple）；
3. 用户名 + 密码登录；
4. 邮箱 + 密码注册和登录；
5. 邮箱验证与密码重置。

账号系统必须满足：

- Apple 登录与 Google 登录具有等价入口和基本能力；
- 一个用户账号可以绑定多个登录方式，避免产生多个孤立账号；
- 第三方账号以服务商返回的稳定用户 ID 为准，不能只用邮箱判断身份；
- 用户名大小写不敏感且全局唯一；
- 邮箱保存前进行规范化，并完成所有权验证；
- 密码只在服务端保存安全哈希，不得明文保存或记录；
- 登录 Token 在移动端使用 iOS Keychain / Android Keystore 对应的安全存储，不使用普通本地配置文件；
- 不在日志、崩溃报告或分析事件中记录密码、Token 和完整邮箱；
- 支持退出登录、撤销第三方绑定和 App 内删除账号；
- 删除账号时同步删除或匿名化该用户的收藏、历史及其他个人数据；
- 第一版首页原型不要求实现登录，但后续架构不得阻碍以上能力。

## 5. 隐私与数据最小化

- 只收集账号、同步和用户主动提交功能所必需的数据；
- 不申请通讯录、相册、定位、麦克风、相机等与核心功能无关的权限；
- 第一版不接入广告 SDK、用户画像 SDK或跨 App 追踪；
- 第一版不接入非必要的第三方行为分析 SDK；
- 崩溃监控如后续接入，必须过滤账号、Token、邮箱和用户输入；
- 收藏、浏览历史默认属于用户个人数据，不用于出售、广告定向或商业推荐；
- 上架前必须准备可公开访问的隐私政策、用户协议和账号删除说明；
- API 全程使用 HTTPS，生产环境不得使用测试证书或关闭证书校验。

## 6. UI 与用户体验规范

### 6.1 设计原则

- 以现有移动端 Web 视觉为第一版参考，保持品牌、色彩、卡面和整体氛围；
- 复刻的是视觉意图和信息层级，不是机械复制 CSS 像素；
- iOS 和 Android 可以在返回手势、触觉反馈、系统弹窗等方面遵循各自平台习惯；
- 页面必须适配刘海、Dynamic Island、圆角屏、底部手势区和 Android 系统栏；
- 所有主要点击区域不小于 44×44 逻辑像素；
- 页面必须支持系统字体缩放，关键内容不得因大字体被截断；
- 颜色和文字对比度应满足基本无障碍要求；
- 图标按钮必须提供语义标签；
- 支持系统“减少动态效果”设置，为复杂动画提供降级模式；
- 加载、空状态、失败、离线和重试状态必须作为正式 UI 设计，而不是临时提示；
- 动画用于表达层级与状态变化，不为了展示技术而阻碍操作。

### 6.2 性能目标

- 常规滚动和页面切换以稳定 60 FPS 为最低目标；
- 支持高刷新率设备时，应争取 90/120 FPS；
- 首屏不得等待全部卡片图片下载完成后才显示；
- 图片按显示尺寸解码并使用缓存，避免加载原始超大图；
- 重绘范围应受控，避免整个页面因单个动画持续重绘；
- 动画和手势必须在至少一台真实 iPhone 与一台中低端 Android 真机验证；
- 不能只以模拟器流畅作为验收依据；
- 性能不达标时优先降低非必要粒子数量、模糊半径或背景复杂度，不牺牲触控响应。

## 7. 第一版 Flutter 原型范围

第一版不是完整 App，也不是上架版本。它的唯一目标是验证 Flutter 能否高质量复刻当前首页体验。

### 7.1 必须完成

- 建立可分别运行于 iOS 和 Android 的 Flutter 工程；
- 建立基础主题、颜色、字体、间距和图标规范；
- 复刻全屏背景、氛围光效和安全区处理；
- 复刻首页顶部区域：
  - “我的卡片”标题；
  - 当前用户/演示状态说明；
  - 右上角添加按钮；
- 复刻首页主体：
  - 卡片堆叠展示或空状态；
  - 基本进入动画；
  - 点击、按压反馈；
- 复刻底部导航栏：
  - 我的卡片；
  - 市场；
  - 排行榜；
  - 我的；
  - 独立的添加按钮；
- 首页导航项需要有选中状态、按压反馈和正确的安全区间距；
- 非首页导航项第一版可以进入统一占位页，但不能出现无响应点击；
- 使用本地 Mock 数据，不依赖生产 API；
- 同时提供“有卡片”和“无卡片”两种可验证状态；
- 在至少一台 iPhone 和一台 Android 真机上录制或截图对比现有 Web 版本。

### 7.2 第一版明确不做

- 不实现注册和登录；
- 不接入 Google Sign-In 或 Sign in with Apple；
- 不接入正式 API 和账号同步；
- 不迁移市场、排行、详情、文章和个人中心业务；
- 不实现管理后台；
- 不实现推送、深链、订阅、支付或广告；
- 不追求一次性迁移 Three.js 粒子卡片效果；
- 不为了赶进度使用整页 WebView。

## 8. 第一版验收标准

满足以下条件后，才能判断 Flutter 方案可行并进入下一阶段：

- iOS 和 Android 均能独立构建、安装和启动；
- 首页布局与现有 Web 版在信息层级、品牌氛围和主要尺寸关系上基本一致；
- 底部导航不会被系统手势区遮挡；
- 列表滚动、页面切换、卡片按压没有明显掉帧或延迟；
- 无卡片状态和有卡片状态都完整可用；
- 深色背景、渐变、玻璃效果在两端无明显色差或渲染异常；
- 开启大字体和减少动态效果后仍能完成基本操作；
- 首页没有 WebView、DOM 或远程网页依赖；
- Flutter 原型不会修改或破坏现有 Vue Web 项目。

如果第一版未达到体验要求，应先定位是实现问题、资源问题还是 Flutter 渲染限制，再决定是否继续；不得因为已经投入开发而默认进入全量迁移。

## 9. 后续阶段建议顺序

第一版通过验收后，再逐阶段确认范围：

1. 市场列表、搜索和筛选；
2. 卡片详情与普通卡面动效；
3. 用户名/邮箱注册登录；
4. Google Sign-In 与 Sign in with Apple；
5. 收藏、历史和“我的卡片”账号同步；
6. 排行榜、文章和反馈功能；
7. 推送提醒、离线缓存与复杂动效；
8. 上架合规、隐私材料和商店审核准备。

每个阶段都必须延续本文件的个人账号、非商业化、信息工具和体验优先原则。

## 10. 开发变更纪律

- 新功能开发前必须检查是否违反第 2、3、4、5 节；
- 涉及登录、隐私、外链、金融数据或系统权限的变更必须同步更新本文档；
- 任何可能被理解为金融服务、商业推广或用户敏感数据处理的功能，不得直接进入开发；
- 产品范围不明确时，默认采用更少权限、更少数据和更低合规风险的方案；
- 本文档中的“不可擅自变更”内容只有项目所有者明确确认后才能修改；
- 第一版开发期间不得顺带扩展市场、详情、会员、支付或后台功能。

## 11. 待第一版开始前确认

以下内容尚未决定，不应由开发者自行假设：

- App 中文名和英文名；
- iOS Bundle ID 与 Android Application ID；
- 最低支持的 iOS 和 Android 系统版本；
- Flutter 项目的状态管理、路由和依赖注入方案；
- 首页第一版默认展示哪些 Mock 卡片；
- App 图标和启动页最终设计；
- 是否首发即支持中英文；
- 数据服务的生产部署方式。

这些事项不阻碍先制作首页视觉原型，但在正式工程结构或商店配置完成前必须逐项确认。
