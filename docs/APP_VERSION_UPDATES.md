# App 版本更新与强制更新

版本更新由 Web 管理端配置、服务端判定，Flutter 只消费服务端返回的更新状态。iOS 与 Android 独立配置，不能用一端的版本号替代另一端。

## 管理端字段

- `latestVersion` / `latestBuildNumber`：商店当前可下载的最新版本；两项必须同时填写。
- `updateUrl`：对应 App Store 或 Google Play 的 HTTPS 地址。启用版本检查时必填。
- `releaseNotes`：展示给用户的本次更新说明。
- `forceUpdateEnabled`：是否启用强制更新，默认关闭。
- `minimumVersion` / `minimumBuildNumber`：强更开启时的最低支持版本；两项必须同时填写，且不能高于最新版本。

服务端比较时先比较版本号的数字段，再比较构建号。例如 `1.1.0 (1)` 高于 `1.0.9 (999)`；同版本号下，构建号更大的版本更新。

## 判定规则

| 当前安装包 | 强更开关 | 返回状态 | App 行为 |
| --- | --- | --- | --- |
| 不低于最新版本 | 任意 | `upToDate` | 不提示 |
| 低于最新版本 | 关闭 | `optional` | 可跳过提示；同一目标版本不重复弹出 |
| 低于最新版本但不低于最低支持版本 | 开启 | `optional` | 可跳过提示 |
| 低于最低支持版本 | 开启 | `required` | 不可关闭、不可返回，只能前往商店更新 |
| 未配置最新版本 | 任意 | `unavailable` | 不检查、不阻断 |

旧数据没有 `forceUpdateEnabled` 字段时，如果已经填写完整的最低支持版本，服务端会兼容为“强更开启”，避免部署新版服务端时静默改变线上策略。管理员下一次保存后将写入明确布尔值。

## 防误锁保护

1. 管理端开启强更时必须配置最新版本、最低支持版本和 HTTPS 商店链接。
2. 保存包含强更的平台前必须二次确认，并提醒先验证商店版本可下载。
3. Flutter 只接受带有效主机名的 HTTPS 更新地址。如果服务端意外返回强更但链接无效，客户端会降级为不阻断，并在“版本管理”页显示配置异常。
4. 网络失败或服务端不可用时采用 fail-open，不阻断用户使用；版本检查恢复后重新执行策略。
5. 强更只应处理安全漏洞、服务端协议不兼容或无法继续支持的旧版本，普通功能更新保持可选。

## 安全发布顺序

1. 先将新包提交 App Store / Google Play，并等待审核完成。
2. 从非开发者账号、不同网络的真实设备确认商店页面和新包均可下载。
3. 管理端先填写最新版本、构建号、HTTPS 链接和说明，保持“强制更新”关闭并保存。
4. 用旧包确认出现可选更新、跳转正确，新包确认显示“已是最新版本”。
5. 确有必要时，再开启强更、填写最低支持版本并二次确认保存。

## 回滚

出现商店链接、审核分发或新版本稳定性问题时，优先在管理端关闭“强制更新”并保存。这样旧包会立即恢复为可选更新，无需重新发布客户端。若整个版本不应再提示，可清空对应平台的最新版本、构建号和更新链接。

## 真机验收

- iOS、Android 分别覆盖 `upToDate`、`optional`、`required`、未配置和断网状态。
- 可选更新能够选择“稍后”，且同一目标版本不在每次启动重复弹出；目标版本变化后重新提示。
- 强更弹窗不能点遮罩、系统返回键或手势关闭，商店按钮跳转正确。
- 320dp 窄屏、130% 字体和减少动态效果下，版本说明及按钮仍可操作。
- 在系统商店仍未完成分发时，不得开启强更。
