# 个人卡片与消费账本

更新时间：2026-10-07。客户端和独立服务已实现；未部署到生产环境。

## 用户入口

- 已添加卡片的详情 → 更多操作 → 管理这张卡。
- 我的 → 我的账单 → 消费账本：手动记账、管理个人卡片和月度统计。
- 识别结果或历史账单详情 → 记入消费账本：选择个人卡片、核对、保存。
- 消费流水 → 更多操作 → 记录退款 / 记录返现，自动关联原消费。

首页卡面和手势保持现有行为；个人卡片实例在管理页中展示。
旧 `myCardIds` 仍代表目录产品收藏，不写入个人卡片资料，不自动推断持有关系。
用户可为同一产品添加多张个人卡片；每张都有独立 ID，末四位可以为空或重复。
归档保留流水；有流水的卡片不能直接删除。退款与返现可以在归档后继续补录。

## 账单与记账口径

- 消费保存原始消费金额与实际扣款，统计仅使用实际扣款，避免双计。
- 金额使用十进制字符串，最多 12 位整数、8 位小数；服务端以 BigInt 定点数求和。
- 原始消费与扣款金额独立；不同币种分别汇总，不自动折算为人民币。
- 手续费明确为已含或额外收取。已含手续费只作分类展示，不再次增加净支出。
- 手续费汇总仅计算已记录的费用；未填写不表示发卡方没有收费。
- 实际返现和退款是关联消费的独立流水，以到账/退款日期所属月份统计。
- 预计返现使用 `pending`；`draft`、`pending`、`failed` 都不计入正式汇总。
- 退款使用原扣款币种，已入账和处理中退款合计不得超过原扣款。
- 有关联退款或返现时，不允许删除原消费；修改原消费仍校验所有关联关系。
- 净支出 = 消费实际扣款 + 额外手续费 + 独立手续费 − 已入账退款 − 已到账返现。
- 月度统计由服务端查询完整数据，不受列表分页和流水状态筛选影响。
  币种筛选应用于汇总币种；列表按实际扣款币种筛选。

原识别历史继续由原 API 保存。导入前再次读取当前账号有权访问的原记录；
用户必须核对归属和数值，才能保存到消费账本。识别来源、原记录版本及有限金额
快照不可修改；记账值可修改。导入默认待确认，选择“已入账”后才计入统计。
识别中的手续费可能有多种口径，因此由用户补充并确认是否已含；返现另行确认到账。
识别为退款的账单需从原消费的“记录退款”入口补录，不能直接作为新消费导入。
同一账号同一识别账单只能存在一份账本记录。两边保存后独立，不自动覆盖或同步修改。
旧版估算损耗/汇率功能保持原有展示，月度净支出不使用变化中的当前参考汇率。

导入按账单上标示的日历日期归属月份，时区偏移不改变日期；缺少有效日期会提示
核对。识别缺少扣款币种时必须补填，不默认猜测为人民币。来源快照中的缺失或无效
金额保留为空，不妨碍用户核对并填写有效记账金额。已保存导入的同请求重试不再
依赖原账单可用性，避免网络中断后误报保存失败。

表单滚动后仍校验全部字段，并滚动到首个错误位置；保存期间阻止重复操作与返回。
补记或改为其他月份后，列表跟随保存的日期并移除不匹配的筛选。归档卡片入口不能
新增消费，仍可从原消费补录退款与返现。列表在窄屏/大字体下改为纵向卡片布局，
卡片选择优先显示末四位；账本页支持系统返回、iOS 边缘返回和减少动态效果。

## 架构与兼容

Flutter 模块位于 `lib/features/ledger/`；服务位于本仓库 `server/ledger/`。
该服务使用 Node.js 24+ 内置 HTTP、SQLite 和加密模块，没有新增 npm 依赖。
旧 Vue 项目和旧账单接口完全不需要修改。新服务使用现有 Supabase 项目验证
短期访问令牌，仅接受已验证邮箱账号；用户 ID 由认证结果确定，不接收客户端 owner。

默认 `ENABLE_PERSONAL_LEDGER=false`，不会在已发布版本中意外开放新入口。
服务端默认 `LEDGER_ENABLED=false`，两个开关必须同时开启。

每个用户的数据在 SQLite 中以 AES-256-GCM 密文保存，记录包含随机 IV、认证标签和
用户关联数据。数据库中的用户键为 HMAC 摘要。密钥只在服务端，不能加入客户端
构建参数、仓库或日志。应用不把个人账本持久缓存到普通偏好设置。
数据库事务保护并发写入；修改/删除检查 `expectedRevision`，创建使用稳定请求 ID
保证重试幂等。单账号上限 240 张卡、5000 笔流水，初期部署使用单服务实例和本地磁盘。

## 接口

所有公开接口均在 `/api/user/card-ledger` 下，使用 Bearer Token，响应 `no-store`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET / POST | `/cards` | 列出 / 创建个人卡片 |
| PATCH / DELETE | `/cards/:id` | 修改 / 删除无流水的卡片 |
| GET / POST | `/entries` | 分页查询 / 创建流水 |
| PATCH / DELETE | `/entries/:id` | 修改 / 删除流水 |
| GET | `/summary` | 完整月份、指定卡片及币种的汇总 |
| DELETE | 根路径 | 账号删除前清除全部账本数据并禁止旧请求重新写入 |

查询支持 `month=YYYY-MM`、`userCardId`、`currency`；流水另支持 `state`、
`cursor`、`limit`（最多 100）。月度归属采用用户确认的 `occurredOn=YYYY-MM-DD`，
不因查看设备的时区变化重新划分日期。

创建体包含 `requestId`；修改和删除必须包含 `expectedRevision`。
服务端拒绝跨用户关联、完整卡号字段和自由文本中的连续长号码；卡号末四位仅接受
4 位数字或空值。原图、模型原文、凭据和任意嵌套识别对象不进入账本。

## 本地验证与上线配置

```powershell
node --test server/ledger/test/*.test.mjs
flutter test --no-pub test/ledger_test.dart
```

服务环境变量模板为 `server/ledger/.env.example`。安全配置：

1. 配置现有认证项目的 `SUPABASE_URL` 和公开 `SUPABASE_ANON_KEY`。
2. 使用安全随机源生成独立的 32 字节十六进制 `LEDGER_ENCRYPTION_KEY`，另生成
   至少 32 字符的 `LEDGER_DELETION_SECRET`；不要放入 Flutter 配置。
3. 设置持久磁盘上的 `LEDGER_DATABASE_PATH`。数据库、WAL、备份仅服务账号可访问；
   加密密钥需独立保管并备份，丢失后无法恢复数据。不要把文件放进 Web 静态目录。
4. 使用 `node --env-file=<受保护的环境文件> server/ledger/index.mjs` 启动。
   默认仅监听 `127.0.0.1:51713`；公网只通过 HTTPS 反向代理暴露指定路由。
5. 将 `/api/user/card-ledger` 及子路径反向代理到新服务；原 API 路由保持不变。
   导入通过 `CARD_API_ORIGIN` 读取原账单，其值必须是受信任的 HTTPS origin。
6. 接好下述账号删除回调；验证后设置服务端 `LEDGER_ENABLED=true`。
7. 复制 `config/ledger.example.json` 到被忽略的 `config/ledger.local.json`，
   构建时添加 `--dart-define-from-file=config/ledger.local.json`，同时保留原认证配置。
   默认使用现有 API 域名；如服务独立域名，增加 `LEDGER_API_BASE_URL`，必须为 HTTPS。

没有服务或认证配置时，不伪造保存成功，不创建演示个人账本。
客户端单独开启只会得到可重试的不可用状态。

## 账号删除、隐私和上线门槛

新版 App 删除账号时，先清除账本再调用原账号删除接口。除了明确的 404（没有部署
该服务），任何账本清除错误都会中止账号删除，允许用户重试。清除后有永久删除标记，
已验证但仍在执行的旧请求不能把数据重新创建。若随后账号删除失败，需要重试完成
删除；不自动恢复已删除数据。

旧客户端或管理后台也可能删除账号，部署时必须在可信身份删除流程中接入：

`POST /api/internal/card-ledger/account-deleted`

- JSON：`{"userId":"<已删除的 Supabase user.id>"}`。
- `x-ledger-timestamp`：当前 Unix 毫秒时间戳。
- `x-ledger-signature`：使用 `LEDGER_DELETION_SECRET` 对字符串
  `${timestamp}.${userId}` 做 HMAC-SHA256 后的十六进制摘要。
- 接受 5 分钟时间窗，可重复投递；身份删除任务应持久重试直到 200。
- 该精确路径可经 HTTPS 代理，必须保留签名验证；禁止直接暴露数据库目录。
- 服务关闭新功能时，删除接口仍然可用。

删除回调接线、生产部署、备份保留/删除策略和真机验证尚需在部署环境完成。
不要仅以配置了回调密钥代替验证投递成功。旧版账号删除必须一并测试。
隐私政策上线文案应披露个人卡片末四位、消费记录、独立存储目的、删除方式及
实际采用的备份保留期限；数据库恢复后要重放删除事件，防止恢复已删除账号数据。

上线验证需覆盖：两账号隔离、同款多卡、识别导入/重复导入、分币种/跨月统计、
并发修改、断网重试、归档退款、账号切换、账号删除、窄屏、大字体、浅深色和双端返回。
